# 08 — Summary for collaboration

This capture documents an IoT observation path across a Raspberry Pi, a ChirpStack/Mosquitto cloud host, and a Magistrala/SuperMQ platform host.

The goal was to empirically show how the headers change across the path.

The key finding is that the observation does not travel with one single end-to-end header. Instead, it is re-encapsulated at each service boundary.

The observed path is:

```text
RPi sensor script
  → MQTT/TCP
  → Mosquitto/ChirpStack host
  → MQTT/TCP
  → Python adapter
  → HTTP/SenML
  → Magistrala/SuperMQ internal services
  → NATS / writer
  → TimescaleDB
```

At the first boundary, the data appears as MQTT over TCP/IP:

```text
IP header
  → TCP header
    → MQTT publish
      → sensor payload
```

At the adapter boundary, the same logical observation is transformed into HTTP/SenML:

```text
IP header
  → TCP header
    → HTTP POST
      → HTTP headers
      → SenML JSON payload
```

Inside the platform, the data is represented by internal service protocols:

```text
NATS messages
PostgreSQL/TimescaleDB traffic
```

A LoRaWAN packet forwarder process exists on the Raspberry Pi, but it points to TTN rather than directly to the private ChirpStack/Magistrala path captured here. Therefore, the validated production path to the platform begins with MQTT generated by the RPi-side sensor script.

The most useful capture files for understanding the protocol/header transitions are:

```text
G1_RPI_GATEWAY_ANY_MQTT_AND_UDP1700.pcap
C1A_CHIRPSTACK_EXTERNAL_ENS3.pcap
C2A_MAGISTRALA_EXTERNAL_ENS3.pcap
C2B_MAGISTRALA_DOCKER_BRIDGE.pcap
```

The `C2B` Docker bridge capture is especially useful because it shows the transition from adapter-generated HTTP/SenML to the internal Magistrala/SuperMQ pipeline.

# 01 — Experiment overview

## Objective

This capture documents a real IoT data path from a Raspberry Pi sensor/gateway host to an IoT platform deployed in the cloud.

The immediate motivation was to answer a concrete question: **what do the headers look like along this IoT path?**

The answer is not a single packet header. The sensor observation is progressively represented through different protocol layers and service domains. At each stage, the same logical observation is wrapped by a different transport or application protocol.

## Run

```text
Run ID: lorawan-e2e-r04-20260429
```


Each host wrote packet captures, logs, metadata, clock information, process inventories, and validation summaries.

## What was validated

The main production path observed in this run is:

```text
RPi / EnvData.py
  → MQTT over TCP
  → cloud Mosquitto/ChirpStack host
  → MQTT over TCP
  → Python adapter
  → HTTP/SenML
  → Magistrala/SuperMQ
  → NATS/internal services
  → TimescaleDB/PostgreSQL
```

This path was validated by observing:

1. MQTT messages from the RPi to `177.104.61.23:1883`;
2. MQTT traffic between `177.104.61.23:1883` and the adapter host `177.104.61.21`;
3. HTTP `POST /m/.../c/...` requests from the adapter into the Magistrala/SuperMQ HTTP adapter;
4. `HTTP/1.1 202 Accepted` responses from the platform;
5. internal traffic involving NATS and the Timescale writer/database.

## Important clarification about LoRaWAN

A LoRaWAN packet forwarder process exists on the RPi. However, its configuration points to TTN (`au1.cloud.thethings.network`) rather than directly to the private ChirpStack/Magistrala path used in this capture.

Therefore, for this particular end-to-end platform path, the RPi-side relevant data transmission is MQTT generated by `/home/mist/Software/EnvData.py`, not UDP 1700 from the packet forwarder to `177.104.61.23`.

The packet forwarder was still included in the inventory and filters because it is part of the gateway environment and may be relevant in future captures.
